# SMTP-protocol

# Завдання 1: Дослідження SMTP протоколу «вручну» через telnet

## 1) Що таке SMTP і на якому транспортному протоколі (TCP/UDP) він працює?

SMTP — це текстовий протокол. Сервер та клієнт обмінюються ASCII-командами. Він працює на TCP протоколі.

## 2) Яка різниця між командами HELO і EHLO?

HELO (Hello) — це застаріла команда для базового SMTP, а EHLO (Extended Hello) — сучасна команда для розширеного SMTP (ESMTP). Різниця між ними у безпеці та можливостях: HELO просто починає передачу тексту, а EHLO дозволяє зашифрувати лист та ввести пароль.

## 3) Навіщо потрібна крапка . на окремому рядку наприкінці повідомлення?

Крапка на окремому рядку — це сигнал кінця повідомлення. Закінчення діалогу.

## 4) На яких портах зазвичай працює SMTP? Чим відрізняються порти 25, 465, 587?

**Порт 25 (Основний SMTP)** — для передачі пошти між серверами.

**Порт 587 (Сучасний стандарт відправки)** — для відправки листів користувачами (сучасний стандарт).

**Порт 465 (Застарілий, але популярний SSL)** — для відправки листів користувачами (через захищений SSL).

# Завдання 2: SMTP-коди відповідей та команди

## 1. Таблиця основних SMTP-команд

| Команда | Призначення | Приклад |
|----------|-------------|----------|
| EHLO/HELO | Привітання та ідентифікація клієнта | `EHLO mail.example.com` |
| MAIL FROM | Вказати адресу відправника (конверт) | `MAIL FROM:<user@example.com>` |
| RCPT TO | Вказати адресу отримувача (конверт) | `RCPT TO:<admin@example.com>` |
| DATA | Почати передачу тіла листа | `DATA` |
| QUIT | Завершити з'єднання | `QUIT` |
| AUTH | Аутентифікація користувача за логіном і паролем | `AUTH LOGIN` |
| STARTTLS | Шифрування поточного відкритого з'єднання за допомогою TLS або SSL | `STARTTLS` |
| RSET | Скасовує поточний лист і очищає дані, але залишає з'єднання відкритим для нової спроби | `RSET` |
| VRFY | Перевірка існування конкретної поштової скриньки на сервері | `VRFY admin@example.com` |

## 2. Таблиця кодів відповідей SMTP

| Код | Значення | Коли зустрічається |
|------|-----------|-------------------|
| 220 | Сервер готовий до роботи | При підключенні до сервера |
| 221 | Сервер завершує роботу | У відповідь на QUIT |
| 250 | Запитана дія виконана | Після EHLO, MAIL FROM, RCPT TO |
| 354 | Починайте передачу листа | У відповідь на DATA |
| 421 | Сервіс недоступний | Коли сервер перезавантажується або перевантажений |
| 450 | Поштова скринька недоступна | Коли файли одержувача заблоковано іншим процесом |
| 500 | Синтаксична помилка команди | Якщо неправильно написана команда |
| 550 | Поштова скринька не знайдена або недоступна | Коли такої адреси одержувача не існує або блокування листа через спам-фільтр |
| 552 | Перевищено ліміт пам'яті | Коли поштова скринька повністю переповнена |

## 1) Чим відрізняються коди 4xx від 5xx у SMTP?

- 4xx - це тимчасові помилки, помилки на боці сервера (немає місця, збій мережі). Клієнт має спробувати пізніше.
- 5xx - це постійна помилка. Запит не може бути виконаний (немає такої адреси, спам). Повторна спроба не має сенсу.

## 2) Що означає код 354 і чому він відрізняється від 250?

- Код 250 (OK) — це остаточна відповідь про успіх. Сервер повністю виконав команду (наприклад, записав адресу) і чекає на нову команду.
- Код 354 — це «Продовжуй». Сервер каже, що команда DATA ще не закінчена, і він чекає на текст листа.
- 250 закриває поточний крок, а 354 відкриває режим очікування вмісту, який завершиться лише після відправки крапки.

## 3) Що станеться, якщо сервер поверне 550 у відповідь на RCPT TO?

Це означає, що лист цьому одержувачу доставлено не буде. Процес для цієї конкретної адреси негайно припиняється.

На практиці це означає, що адреса не існує або лист заблоковано (спам / чорний список).

# Завдання 3: Структура email-повідомлення (RFC 5322)

## 2. Таблиця заголовків листа

| Заголовок | Призначення | Обов'язковий? |
|------------|-------------|---------------|
| From | Адреса відправника | Так |
| To | Адреса(и) отримувача | Так |
| Subject | Тема листа | Ні |
| Date | Дата та час відправки | Так |
| Message-ID | Унікальний ідентифікатор листа | Ні |
| Cc | Адреса(и) отримувачів копії листа | Ні |
| Bcc | Адреса(и) отримувачів прихованої копії | Ні |
| Reply-To | Адреса, на яку буде надіслано відповідь | Ні |
| MIME-Version | Версія стандарту мультимедійного розширення пошти | Ні |
| Content-Type | Тип даних у листі (текст, HTML, кодування, вкладення) | Ні |

## 1) Що таке MIME і навіщо він потрібен для email?

- MIME - це технічний стандарт, який розширює можливості електронної пошти для передачі різноманітного контенту. Без MIME електронна пошта могла б передавати лише сухий неформатований текст без файлів. Стандарт MIME забезпечує такі ключові функції:

  * Надсилання вкладень: дозволяє додавати до листів будь-які файли.
  * Підтримка HTML-верстки: завдяки MIME листи можуть мати оформлення, шрифти, кольори, кнопки та вбудовані зображення.
  * Будь-які мови та кодування: дозволяє використовувати кирилицю та інші національні алфавіти замість базової латиниці.
  * Мультиформатність (Multipart): дозволяє поєднувати в одному листі кілька версій контенту.

## 2) Чим відрізняються To, Cc та Bcc на рівні SMTP-протоколу?

На рівні SMTP-протоколу різниці між To, Cc і Bcc не існує — всі одержувачі передаються через RCPT TO.
Різниця є лише на рівні MIME-заголовків: To і Cc відображаються в листі, а Bcc видаляється і використовується лише на етапі доставки для прихованих одержувачів.

## 3) Що означає Content-Transfer-Encoding: base64 і чому вкладення кодуються у base64?

Content-Transfer-Encoding: base64 означає, що конкретна MIME-частина листа передається у вигляді Base64 і повинна бути декодована назад у байти на стороні отримувача.

Це використовується для передачі двійкових даних (зображень, PDF, архівів) через SMTP, який історично працює з 7-bit ASCII і не гарантує коректну передачу довільних байтів.

Base64 не змінює зміст даних, а лише перетворює їх у текстовий формат для транспортування. Недолік — збільшення розміру приблизно на 33%.

## 4) Чи може адреса у From заголовку відрізнятися від адреси у MAIL FROM? Які наслідки?

- Так, адреса у заголовку From: може повністю відрізнятися від адреси у команді MAIL FROM. MAIL FROM і From виконують різні функції:

* MAIL FROM — адреса відправника на рівні SMTP-конверта. Використовується для доставки повідомлень про помилки (bounce).
* From — адреса, яку бачить користувач у поштовому клієнті. Адреса відправника

# Завдання 4: Відповідь на питання

## 1) Чому SmtpClient вважається застарілим у .NET?

- Клас SmtpClient вважається застарілим, оскільки він має застарілу архітектуру, погано підтримує сучасні протоколи безпеки (такі як TLS 1.2/1.3 та OAuth2) і не забезпечує належної асинхронності.

## 2) Що робить метод SendMailAsync порівняно з Send?

- Метод SendMailAsync надсилає лист асинхронно, тоді як Send надсилає синхронно. Завдяки асинхронності наш застосунок не буде блокуватись під час надсилання листа.

## 3) Чим відрізняються MailMessage.Body та AlternateViews?

- Головна різниця полягає в кількості форматів представлення листа та гнучкості для поштових клієнтів. Body — це завжди один конкретний текст повідомлення, тоді як AlternateViews — це колекція, яка дозволяє надіслати один і той самий лист одразу в кількох форматах.
